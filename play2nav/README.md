# play2nav —— HM3D 场景键盘交互导航（网页版）

在浏览器里把 Habitat HM3D 场景显示出来，用键盘 `w/a/d/q/e` 实时驱动机器人走，**轻触走一步、
按住满 1 秒转持续移动**，按 `p` 结束本集并把**录像 / topdown 回放 / 轨迹图 / 指标**落到磁盘。
页面右侧另有一个实时俯视小地图。

跑这个项目的机器没有图形界面（`DISPLAY` 未设、无 Xvfb），所以界面是**网页**：你在自己的电脑上
用浏览器打开它即可，服务端不需要任何显示设备。附带的好处是整条交互链路都落在 HTTP 上，可以
被自动验证（`test_webserver.py`）——而本地窗口做不到。

它和 `test/pix2move/run_pix2move.py` 是**两条并行的链路**，互不替换：

| | 驱动来源 | 用途 |
|---|---|---|
| `test/pix2move/run_pix2move.py` | 文本 → GLEE 分割 → 反投影 → navmesh 贪心跟随 | **感知**研究，跑基线拿 SPL |
| `play2nav/`（本目录） | **人**按键盘 | 人工试玩、录回放、看人走得有多绕 |

本目录**不 import torch / 不碰分割**，只用 RGB 观测，因此启动快、内存小。

## 快速开始

在跑模拟器的那台机器上：

```bash
conda activate harnessnav
cd /home/xsuper/hc_workplace/HarnessNav

python play2nav/app.py                       # 起网页服务（默认 --stage val --episodes 20）
```

启动后终端会打印一行网址，例如：

```
[web] 打开 http://10.12.208.214:8080
```

**在你自己电脑的浏览器里打开这个网址**（同一局域网内即可）。默认监听 `0.0.0.0:8080`，所以
不需要在服务器上做任何转发。

> ⚠️ **页面上没有登录**，同局域网的任何人都能打开并驱动机器人。只在不介意这一点的网络里用。
> 要只给自己用：`python play2nav/app.py --host 127.0.0.1`，再从你的电脑做 SSH 端口转发
> （`ssh -L 8080:127.0.0.1:8080 xsuper@10.12.208.214`），然后开 `http://127.0.0.1:8080`。

产物默认写到 `/DATA_HDD/hc/play2nav_outputs/`（**不要**改到默认路径：`/` 分区只剩十几 GB，
录像累积会撑爆）。

**改了代码要重启服务才生效**（Python 不热加载，页面上看到的还是启动时的旧版本）。停服务用
`Ctrl-C` 或 `kill <pid>` 都行——两者都会把当前这一集按 `quit_early` 正常落盘（`SIGTERM` 被转成了
`KeyboardInterrupt`，走的和 Ctrl-C 同一条收尾路径）。**别用 `kill -9`**：`finally` 不会执行，
正在写的 mp4 会停在半截（48 字节，只有文件头）。

只支持**桌面浏览器**：手机没有键盘，页面也不做虚拟按键。

### 键位

键盘焦点必须在页面上（点一下页面即可）。

| 键 | habitat 动作 | 说明 |
|---|---|---|
| `w` | `move_forward` | 前进 0.25 m |
| `a` | `turn_left` | 左转 30° |
| `d` | `turn_right` | 右转 30° |
| `q` | `look_up` | 抬头 30° |
| `e` | `look_down` | 低头 30° |
| `p` | `stop` | **结束本集并落盘**（按下即触发，不是长按） |
| `Esc` | — | 等同「退出」（会弹一次确认框） |

也可以直接点左边两个按钮：**进入下一个场景** / **退出**。

**轻触一下 = 走一步；按住满 1 秒 = 持续移动**（`--hold-delay`，`0` 退回「一按下就持续动」）。
按下当刻就发**一步**，所以短按永远有反馈（想精确挪一格、想转 30° 就轻点一下）；要连续走才
需要按住。门槛是从**真正按下的那一刻**算起的，前端每秒一次的心跳**不会**重置它、也不会补发
那一步（否则门槛永远跨不过，表现为"按多久都只走一步"，这条有专门的单测守着）。

两条容易写错、也都被单测守住的规则：

- **轻触那一步是「事件」，不是「按住」的一部分**：它欠下了就一定发得出去（上限 2 秒），
  **不要求服务端取键那一刻键盘还按着**。sim 线程走一步要 200 ms 上下（俯视图上色 + 录像编码），
  一次 30 ms 的极短轻触完全可能整段落在这一步的执行期间——要求"取键时还按着"，那一下就
  被静静丢掉，用户看到的是**点了没反应、要再点一下才动**。
- **心跳与真实的按下必须分开**：心跳带 `hb: true`（前端每秒重发按住集合时加上的），服务端
  对它什么都不改；而**不带 `hb` 的按下，哪怕距上一次松手只有几毫秒，也必须是新的一次按下**
  （重新计时、重新拿到一步）。两者在时序上无法区分，只能靠显式标记——把宽限期内的按下当
  心跳吞掉，就是"连点两下只走一步"。

跨过门槛后**按住不放就持续走**，靠「按下集合 + 60 ms 松手宽限」实现，不依赖键盘自动重复的
速率。同时按住多个键时按 `w > a > d > q > e` 的优先级每 tick 只发一个动作。

左侧「输入检测」栏会实时显示倒计时（`按住 w … 0.6s / 1.0s（轻触那一步已出，到点转持续移动）`），
松手时事件流里也会写明「只按了 0.25s，不足 1.0s 门槛 → 只出轻触的一步」。**按了没反应时先看
这一栏**。

浏览器这边有三件事和本地窗口不一样，都是刻意的：

- **切走标签页 / 切到别的窗口 / 关页面，agent 会在 5 秒内自己停下**。浏览器在失焦后可能
  根本不发 `keyup`，所以页面一旦隐藏就主动清键；万一连这条请求都没发出去，服务端还有一个
  **5 秒死人开关**兜底：超过 5 秒没收到**按键事件**（心跳）就松开所有键。注意这个计时
  **只认 `POST /key`，不认 `/state` 轮询**——否则页面自己每 300 ms 一次的轮询会把它永远
  刷新下去（这是实测踩到的）。想让它一直走就别切走。
- **按住期间每秒有一次心跳**。因为浏览器的按键自动重复被页面丢掉了（不丢的话约 30 次/秒，
  每次都是一条新 TCP 连接），光看按键事件分不出「按着」和「客户端没了」——心跳就是那个区分信号。
  它同时也是上面死人开关的计时来源。
- **画面不动时不推流**。agent 站着不动时这条连接是静默的（每 10 秒发一次保活），不占带宽。
  这也是 `/stream` 的自检依据：空闲 3 秒应当**恰好**收到 1 帧。

排障用 `--key-debug`：每 0.5 秒在终端打印一行当前按住的键。

### 界面

```
┌───────────────────────────────────────────────────────────────────────┐
│ 场景: bxsVRursffK  集号 13    需要找的目标: bed    步数: 9 / 2000        │  ← 顶栏
│ ⚠ 碰到障碍物，无法移动…（撞住时才出现，占一整行）                            │
├──────────────┬──────────────────────────────────┬─────────────────────┤
│ 进入下一个场景 │                                  │                     │
│ 退出          │      第一视角 RGB 320×240         │   实时俯视小地图      │
│               │      （MJPEG 流，站着不动就静默）   │   （第二条 MJPEG 流） │
│ 键位 …        │                                  │                     │
│ 状态 …        │                                  │                     │
│ 输入检测 ←新增 │                                  │                     │
└──────────────┴──────────────────────────────────┴─────────────────────┘
```

**两个画面都是常开的 MJPEG 流**（`/stream` 与 `/topdown_stream`），浏览器用原生 `<img>` 吃，
不需要任何脚本。俯视图**曾经**是「每出一帧就换一次 `<img src>`」的轮询——那会在浏览器
**每域名 6 条并发连接**的限制下、每秒新开约 7 条 TCP 连接（MJPEG 那条还常占着一条），
按键请求排在图片请求后面，表现就是**按一下要等 1、2 秒画面才动**。改成第二条流之后按键
POST 走的是另一条已建立的连接，这个队列消失了。

**但每一帧必须切成两段 part 发**（`web.py::Play2NavServer._mjpeg` 里那一帧 `yield` 两次）：
浏览器要等到**更后面一段 part** 到达才把当前这一帧提交上屏。这条流在站着不动时是**静默**的
（不推未变化的帧），所以只发一段的后果是画面永远停在上一步的 obs 上——**按一下键画面不动、
再按一下才显示上一个动作的结果**，一帧一帧地错开。用 Chrome 145 实测过其它写法都没用
（把 boundary 紧跟帧后一起发、连下一段首部一起发、去掉 `Content-Length`），只有"同一帧发
两遍"立刻就对（第二遍内容完全相同，只是把第一遍顶上去）。代价是这一步字节数翻倍。

### 输入检测

左侧「状态」下面那一栏，分三层：

| 位置 | 内容 |
|---|---|
| 实时行（`.live`） | `按住 w … 0.6s / 1.0s（轻触那一步已出，到点转持续移动）`、`按住 w → move_forward 持续输出中`、`没有按键按住（轻触 = 一步；按住满 1.0s = 持续移动）`；**已经松手、但那一步还欠着**时会说「`w` 轻触的一步已收下，待发（sim 线程正在执行上一步）」；下一行是上一步的结果（动作名、位移、有没有接触）；**撞住的提示也在这里** |
| 事件流（`.log`） | 终端式滚动：按下 / 松开 / 清空 / 乱序丢弃 / 死人开关 / **撞住的提示**。松手那条会写明按住时长与这一下按出了什么（「只出轻触的一步」/「超过门槛 → 期间是持续移动」） |
| 诊断行（`.diag`） | **帧号对**（见下）、服务端推送帧率与带宽、两条流的读者数、JPEG 质量与显示比例、`/state` 往返耗时 |

诊断行里的 **`画面帧 第一视角 已推/当前 · 俯视图 已推/当前`** 是「画面有没有落后」的唯一
判据：两个数相等 = 画面已经追上最后一次输入；左边的数落后（前面会出现 `⚠`）说明还有帧在
路上，它会在一两步之内补上（补帧机制见「界面延迟」）。这一对数是为"画面停在旧结果上、
非要再按一下才更新"这类现象加的——**看得见，就不用猜**。

这一栏是「按了没反应」时唯一能自己查出原因的地方，排障顺序：
**① 实时行有没有按键**（没有 → 键盘焦点不在页面上）→ **② 轻触那一行有没有出** →
**③ 有没有「待发」那句**（有 → 那一步在路上，sim 线程正在跑上一步，等一两百毫秒）→
**④ 事件流里松手那条说的是「只出轻触的一步」还是「持续移动」** → **⑤ 有没有撞住的提示**。

### 撞住时页面怎么提示

机制（出生点为什么会被顶住、为什么不改成滑行）见下面「出生点可能"顶着墙"」一节，这里只说
页面怎么把它讲出来。

HM3D 的出生点可能正顶着家具，此时按多久 `w` 都不动——实测某个 episode 连发 **20** 次
`move_forward` 总共只挪 **0.4501 m**（头两步就走满了，之后一步不动）。**这不是 bug，也不是
死机：转身就能走**（实测转向从不碰撞）。

所以页面会明说，而不是让你对着「按 w 没反应」猜。提示同时出现在三处：顶栏横幅、输入检测的
实时行、以及输入检测的**滚动事件流**（所以事后能看出是哪一步开始撞住的）。文案是
「⚠ 碰到障碍物，无法移动（本步位移 0.000 m）…按住 a 或 d 转身，再按 w」。

判据就是**前后位置相同**：`env.step` 发完这一步之后机身坐标一模一样（`STUCK_EPS_M = 1e-4 m`
只是给浮点噪声留的余地，不是经验阈值——`allow_sliding` 关着，被挡住时位移是**真的** 0，
实测连发 20 次前进步里，头两步之后每一步的位移都精确到 0.0000 m，而正常一步是 0.25 m，
两者之间没有任何中间值）。

**没有**把 habitat 的 `collisions.is_collision` 当判据——那是**接触**标志，在有家具的房间里
正常直行也会擦到椅腿、门框（实测每步走满 **0.29 m** 时它照样为真），拿它当闸门会一路误报。
它只作为旁证出现在实时行里（「（有接触）」）。

### 界面延迟

页面卡不卡取决于两件事，都可以调：

- **服务端每步的开销**。实测 `env.step` 52.8 ms，而俯视地图 `colorize_topdown_map` 一次
  **48.7 ms**（整张地图 + 迷雾，一步之内几乎不变）。所以上色结果被缓存、默认每 `0.2` 秒
  （`--topdown-refresh`）才重算一次，中间每步只做 `canvas.copy()`（0.3 ms）；而且**第一视角
  画面在昂贵的俯视图与 mp4 编码之前就推出去**，可见延迟不会被它们拖住。
- **带宽**。实测 640×480 q80 = **27 KB/帧**，480×360 q70 = 12 KB，320×240 q70 = **7 KB**。
  默认 `--display-scale 0.5 --jpeg-quality 70` ≈ 7 KB/帧（录像仍是原始分辨率）。
  网络慢就继续调小这两个值，「输入检测」的诊断行里有实时的 KB/s 可以直接对比。

**画面必须收敛到「最后一次输入的结果」，两条路都不许把更新吞掉**：

- 第一视角在 `_emit_frame` 里**紧跟 `env.step`** 推（早于本步最贵的俯视图与 mp4 编码），
  并且 sim 循环每 tick 都拿「`emit_seq` 与已推帧号是否相等」做一次**兜底补推**——编码失败
  或将来漏推一条路径，下一 tick 就会补上（编码异常不会把整个会话带下去）。
- 俯视图按 `--fps` 限速，但限速**只推迟、不吞**（`_TopdownGate`）：窗口期内到达的那一帧会被
  记住，窗口一到立刻补发。早先的写法在窗口期内直接推进了「已发布帧号」，那一帧就**永远丢了**——
  画面停在旧帧上，要等用户再按一下才更新，正是上面那个现象的另一半成因。

两条都在自检里钉住了（`pub_rgb_seq == emit_seq`、`pub_topdown_seq == frame_seq`，以及闸门的
纯逻辑断言）。


「进入下一个场景」会把当前这集按 `quit_early` 结算后再换集；换场景要重载 glb + navmesh
（实测 3～8 秒），期间页面会显示"正在加载场景…"，按钮置灰。按 `p` 之后状态栏会显示本集的
`success / spl / soft_spl / distance_to_goal` 与产物目录名。

**导航过程中不显示 `distance_to_goal`**——那是评测答案，显示等于开卷。它只在结算时出现。
调试需要时用 `--show-distance`。

## 产物

每集一个目录：`{输出根}/{YYYYmmdd_HHMMSS}_{scene}_{epid}_{category}/`

| 文件 | 内容 |
|---|---|
| `rgb.mp4` | **纯净第一视角观测**，无任何叠加。帧数 = 步数 + 1，fps = `--video-fps` |
| `topdown.mp4` | 俯视回放：habitat 原生 topdown 图 + 生长中的轨迹 + 本集最优路线 |
| `trajectory.png` | 终帧俯视图（原始分辨率）+ 完整轨迹 + 最优路线 + 图例 |
| `metrics.json` | 本集指标与逐步动作序列，见下 |

会话级另有 `{输出根}/session_summary.json`：逐集摘要 + `success / spl / soft_spl` 均值。

### 图上的颜色

| 颜色 | 含义 | 谁画的 |
|---|---|---|
| 灰色 | 可行走区域 | habitat |
| 暗红 | 未探索（雾） | habitat |
| 红方块 | 目标物体位置 | habitat |
| 蓝/白箭头 | agent 当前位置与朝向 | habitat |
| **品红** | **agent 走过的轨迹** | 本目录 |
| **橙黄** | **本集 navmesh 最优路线（测地）** | 本目录 |
| **绿点** | **本集起点** | 本目录 |

topdown 图是矩形的（实测 1024×1526，见 `topdown.resize_for_video` 的说明），编码时按长边
缩到 `--topdown-video-size`（默认 512）并补黑边，**不拉伸**——拉伸会让轨迹几何变形，看起来
像走歪了。`trajectory.png` 始终是原始分辨率。

### metrics.json 字段

`scene_id` `episode_id` `object_category` `stage` `seed` `start_time` `end_time`
`wall_time_s` `num_steps` `max_episode_steps` `actions[]` `action_counts{}` `path_length_m`
`start_distance_to_goal` `shortest_path_length` `success` `spl` `soft_spl`
`distance_to_goal` `collisions{count,is_collision}` `terminated_by`
`success_distance` `navmesh_loaded` `episode_dir` `video_fps` `video_frames` `out_dir`

`terminated_by` 取值：`user_stop`（按了 `p`，此时才结算 success/SPL）/ `max_steps`（撞上
2000 步上限）/ `quit_early`（中途点「进入下一个场景」或退出）/ `no_navmesh`。

`path_length_m` 是逐步 `‖pos_t − pos_{t−1}‖` 的累加，与 habitat 自己累计的
`agent_episode_distance` 同口径（可用 SoftSPL 的公式交叉验算，见「验证」一节）。

## 这些参数值得知道

| 参数 | 默认 | 说明 |
|---|---|---|
| `--stage` | `val` | **本机只有 `val` 能跑**，见下 |
| `--host` | `0.0.0.0` | 监听地址。改成 `127.0.0.1` 就只能本机/SSH 转发访问 |
| `--port` | 8080 | 监听端口；被占用时直接报错退出 |
| `--episodes` | 20 | 会话里预备多少集；跑满后会绕回开头（终端有提示） |
| `--out` | `/DATA_HDD/hc/play2nav_outputs` | 产物根目录 |
| `--success-distance` | 1.0 | HM3D ObjectNav 标准；本仓库 YAML 写的是 0.25 |
| `--action-interval` | 0.15 | 长按时两个动作的最小间隔（秒）。调大=走得慢，便于精细操作 |
| `--hold-delay` | 1.0 | **按住满这么久才转持续移动**（轻触一下只出一步）。`0` 退回「一按下就持续动」 |
| `--fps` | 5 | 俯视小地图的**推送**上限（第一视角每出一帧就推，不受它限制） |
| `--topdown-refresh` | 0.2 | 俯视底图重新上色的最小间隔（秒）。上色一次 48.7 ms，是每步最贵的一环 |
| `--jpeg-quality` | 70 | 网页画面的 JPEG 质量。画质/带宽的取舍点 |
| `--display-scale` | 0.5 | 网页画面的缩放（0.5 = 按 50% 编码）。**网络慢就调小**；录像仍是原始分辨率 |
| `--topdown-video-size` | 512 | 小地图与 topdown 回放编码后的长边像素 |
| `--video-fps` | 10 | 两个 mp4 的帧率（只影响播放速度，不影响帧数） |
| `--shuffle` | 关 | 打乱 episode 顺序（默认关是为了让「进入下一个场景」可复现） |
| `--no-save` | — | 不写任何产物，纯试玩 |
| `--key-debug` | — | 每 0.5 秒打印按键状态，排查长按问题 |
| `--show-distance` | — | 状态栏实时显示 `distance_to_goal`（开卷，仅调试） |

画面延迟不满意时的调法，按见效顺序：`--display-scale 0.25`（带宽立刻减半）→
`--jpeg-quality 60` → `--topdown-refresh 0.5`。都是只影响网页画面，**录像分辨率与帧率不变**。

### `--stage` 本机只有 `val` 可用

`train` / `val_mini` 在这台机器上**跑不了**：episode 里的 `scene_id` 形如
`hm3d_v0.2/minival/<scene>/...`，而 minival 的场景实际摆在
`data/versioned_data/hm3d-0.2/hm3d/minival/`——多了一层 `hm3d`，没有任何 `scenes_dir` 取值
能凑出这个路径。缺的是数据摆放，不是配置。

habitat 在这件事上报的错是
`AssertionError: No Stage Attributes exists for requested scene ... in currently specified
Scene Dataset './data/scene_datasets/...'`——它退回了某个相对路径的默认 dataset，错误信息
指向一个和真实原因毫无关系的路径。所以 `play2nav/config.py::check_split` 做了一道预检，在
构造 `habitat.Env` **之前**把话说清楚。

### 出生点可能"顶着墙"

HM3D 的 spawn 有时贴着家具。实测 `bxsVRursffK ep13`：开局正前方就有一个藤编筐，脚本连发
6 次 `move_forward` 全部 `collided=True`，一共只挪了 **0.0834 m**（全部来自第 1 步的
0.0834，后面 5 步是 **0.0000**——「位置一模一样」正是网页现在判「碰到障碍物」的判据）。
这不是 bug——`move_forward` 在开阔方向上是精确的 0.2500 m（已单独测过）。**遇到走不动就先转身**（`a`/`d` 转 30°，实测转身永远不碰撞）。
网页会替你判断这件事并给出提示，见上面「撞住时页面怎么提示」。

顺带一句：`allow_sliding`（撞墙后沿墙滑行）在 habitat-lab 0.3.1 的 Hydra 配置里**没有
暴露**（`habitat_sim.SimulatorConfiguration.allow_sliding` 存在，但 `SimulatorConfig` 里
没有这个字段），要启用就得绕开 `habitat.Env` 自己造 sim，代价太大且会把物理参数改得和
已验证的评测配置不一致。所以**保持 habitat 默认（不滑行）**。

### 「进入下一个场景」跑满后会开始重复

`--episodes N` 采样 N 集，habitat 的 `cycle=True` 在耗尽后从头再来，所以第 N+1 次换集会
重复第 1 集。终端会打印「本集与之前某集重复…加大 --episodes」，看到就加大 N。

（这里踩过一个坑，也是**已修**的：早期版本在构造 `Navigator` 前多调了一次 `env.reset()`
做预检，白吃掉迭代器的一集，导致 `--episodes 3` 实际只出 A、B、C 变成 A、B、B。现在
`main()` 里**故意不**预 reset，`Navigator.start_episode()` 自己会 reset。）

### 指标口径：`distance_to_goal` 量的是 view point，不是物体中心

ObjectNav 的判分口径是 `distance_to: VIEW_POINTS`（`config/habitat/task/objectnav.yaml`，
结构化默认虽是 `POINT`，被任务 YAML 覆盖了）。所以 `success` / `spl` / `distance_to_goal`
量的都是**到最近 view point 的测地距离**，不是到 `episode.goals[0].position`。

这件事有两个实际后果，都已在代码里处理：

1. `goal.position` 常常**不在 navmesh 上**（在物体内部），拿它去 `find_path` 直接失败——
   实测 3 个 episode 里有 2 个如此。所以画最优路线时，终点取的是
   **离 agent 最近的 view point**（`topdown.closest_view_point`）。
2. 挑这个 view point **必须用带 `episode` 的三参数重载**
   `sim.geodesic_distance(agent, [p], episode)`。实测（bxsVRursffK ep13，722 个 view point）：

   | 调用方式 | 最小值 | 落在哪个点 |
   |---|---|---|
   | `geodesic_distance(agent, p)` | 4.4856 | vp717 |
   | `geodesic_distance(agent, [p], episode)` | **1.7526** | vp0 |
   | habitat metric `distance_to_goal` | **1.7526** | — |

   两参数版本偏大 2.7 m、会挑到完全不同的点；只有三参数版本与官方 metric **逐位相等**。
   这也正好成了路径终点的验收判据（见下）。

## 自检（三个都不需要显示器）

```bash
# 1) 网页层端到端：真的起服务、真的打 HTTP、真的跑 env（约 1 分钟）
python play2nav/test_webserver.py
python play2nav/test_webserver.py --keep      # 保留 scratch 产物

# 2) 无头脚本模式：走完全相同的 start_episode → step → record → finalize 路径
python play2nav/app.py --headless --scripted "w,w,w,a,a,w,w,w,p" --stage val --episodes 1 --selfcheck

# 跨场景连续 3 集（专打"换场景后句柄失效"）
python play2nav/app.py --headless --scripted "w,w,w,a,a,w,w,w,p" --stage val \
    --episodes 3 --shuffle --selfcheck --out /DATA_HDD/hc/play2nav_outputs/multiep

# 3) 按键状态机单测（纯逻辑，无需显示器、无需 habitat）
python play2nav/test_keystate.py
```

`test_webserver.py` 在**另一个线程**里发真实 HTTP 请求去打主线程上的 sim 循环（和生产里
「sim 主线程 + Werkzeug daemon 线程」同一个朝向）。它固化的判据里最要紧的是**按键的节奏**：
轻触一下走出**恰好一步**、且门槛之前不会再走第二步，越过门槛后读数**严格递增**，松手后
**不再前进**。上界排除「每 tick 都发一个动作」（不按时间闸门），下界排除「只走出轻触那一步」，
松手后那一条排除「卡键」。这几条是本地窗口时代**从来无法自动验证**的（本机开不了窗口），
现在全部落在 HTTP 上。

「碰到障碍物」的提示是**双向**断言的，不允许两边都对：**每一次取样**只要有位移，提示就必须
不出现（误报是这条最容易犯的错）；末一次取样位置没变 → 提示必须出现，且必须同时出现在
「输入检测」的实时行与滚动事件流里。末项那个分支只看**末一次取样**而不是整段窗口的最大位移
——出生点顶着家具时 agent 仍能先迈出一两步（实测该场景 20 个前进步总共只挪 0.4501 m，两步
之后才彻底停下），拿窗口最大值当「这一集走不走得动」会把这个过程**判反**（第一版就是这么错
的，被这条断言抓住）。

脚本模式的自检输出里每一项的含义：

- `selfcheck` —— `world_xz_to_pixel` 与 habitat 自己的 `maps.to_grid` 逐点比对（64 点），
  抓坐标序写反（写反会让标记**静默**画到画外）
- `verify` —— 句柄是不是 `env.sim.pathfinder` 本身、地图几何有没有过期、轨迹是否落在本场景
  navmesh 边界内。**这一项只有跨场景时才真正有意义**：`--shuffle` 关掉时数据集按场景分组
  迭代，连着几集常是同一个场景，那时全绿也证明不了什么（脚本会提示「与上一集同场景」）
- `goal ref` —— 最近 view point 的测地距离 vs habitat 的 `distance_to_goal`，两者必须一致

### 换场景时页面会僵住几秒（已知，不是 bug）

`env.reset()` 要把 glb + navmesh 重新装进模拟器，这段时间 habitat-sim 在原生代码里**占着
GIL**，于是整个 Python 进程——包括 HTTP 线程——都停摆。实测一次换场景会让 `/state` 整整
**3 秒以上**不应答（`test_webserver.py` 里那个独立进程的探针会把它量出来并打印）。

页面上的表现是：画面与状态停在原地几秒，然后一切恢复正常。因为换场景**之前**服务端已经先把
`phase=loading`（「正在加载场景…」、按钮置灰）推给了页面，用户看到的就是"在加载"，没有误导。

这一条**不是**线程模型的问题——sim 循环在主线程、HTTP 在 daemon 线程，两边没有任何一把锁跨
`env.reset()`（`_web_loop` 里取意图是「取完即释放」）。要消掉这几秒只能把模拟器挪到另一个
**进程**里去，那是另一件事。自检里因此断言的是「换场景结束后服务端**立刻**恢复」，而不是
「换场景期间也一直有响应」。

### 线程模型（改 `web.py` / `app.py` 前必读）

`habitat.Env` **不是线程安全的**，所以：

- **sim 循环在进程主线程**，独占 `env`；**HTTP 服务是 daemon 线程**（Werkzeug），
  **永不接触 `env`**。它只做两件事：改按键状态（一把锁）、置意图标志。
- 意图用**标志**而不是队列：`/stop` 会被重复 POST，队列会攒一堆重复项还要再去重；标志天然幂等。
- sim 线程每 tick 先取锁**拷贝出意图和按键、立刻释放**，再去执行动作。**绝不持锁调
  `env.reset()`**，否则换场景的几秒里每个按键 POST 都会卡住、然后一次性涌入。
- 状态发布是**整体替换一个只含基本类型的 dict**（`server.snapshot`），`/state` 只读一次引用。
  直接去读 `Navigator` 的字段会在换场景期间读到「新 `scene_id` 配旧 `step_idx`」；更危险的是
  `/state` 若去调 `env.get_metrics()`，那就是一边 `env.step()` 一边从别的线程进模拟器——
  那是堆损坏，不是竞态。
- 用 `make_server(...)` 而不是 `app.run()`：**没有 reloader**（reloader 会 fork 出第二个进程，
  等于开两个 `habitat.Env`，显存直接翻倍）。

浏览器那边还有几个坑，都在 `page.html` 里处理了，改动时别删：丢掉 `e.repeat`
（不丢约 30 次/秒的连接）、拦 `Ctrl`/`Meta`/`Alt` 组合键（`Ctrl+W` 会关标签页，`keyup` 永远不来）、
按键请求带**单调 `seq`**（Werkzeug 每个响应都 `Connection: close`，并行请求不保证到达顺序，
`keyup` 早于 `keydown` 就会永久卡住一个键）、失焦/关页面 `sendBeacon('/keys/clear')`
（服务端**必须完全不解析**这条请求体：sendBeacon 发的是 `text/plain`）、按住期间 1 秒一次心跳
（配合服务端 5 秒死人开关）、点击按钮后 `blur()`（否则空格/回车会再触发一次）。

几个实现上值得留意的点：

- **mp4 流式写**，绝不缓存整段：2000 步 × 640×480×3 ≈ 1.8 GB，先攒再编码会把进程吃掉。
  用 `imageio.get_writer(...).append_data(frame)` 边跑边写。
- **`_QuietRequestHandler.disable_nagle_algorithm = True`**：Werkzeug 推一帧分 4 次 `write()`
  （`wbufsize = 0`，无缓冲），Nagle 算法会把后几个小包压住等前一个的 ACK，与延迟 ACK 撞上
  就是每帧固定的几十毫秒停顿。流式画面必须关掉它。
- **一集一个目录、四件产物都在 `finally` 里关干净**：本环境已知解释器**退出时**偶发
  `malloc_consolidate(): unaligned fastbin chunk detected`，指望优雅退出来 flush 是不可靠
  的，没关的 mp4 会直接损坏。
- **`p` 会真的发出 habitat 的 `stop` 动作**。`success`/`spl` 是在**调用 stop 的那一刻**按
  `distance_to_goal ≤ success_distance` 判定的，不发 stop 这两个数恒为 0。另外
  `habitat.Env` 的 `_check_episode_is_active` 只返回 `not is_stop_called`
  （`end_on_success` 只被 Gym 的 `RLEnv` 消费），所以**不按 `p` 本集不会自己结束**。
- **每集重取一切**：`env.reset()` 换场景后 `env.sim.pathfinder` 不报错、照常返回结果，
  但那些结果来自**上一个场景**；topdown 的 `origin/spans` 同理作废。统一收在
  `Navigator.start_episode()` 里，并用 `verify_episode()` 守住院线。
- **不改 `nav/habitat_config.py`**：它第 38 行拼出的 `scene_dataset` 路径实际不存在（真文件在
  `.../hm3d_v0.2/{stage}/` 下一层），habitat 目前靠兜底解析照常工作。这是个潜伏 bug，但既然
  当前链路验证过就不动它，只在 `play2nav/config.py` 里做「路径存在才覆盖」的防御性修正。
- **关掉了 habitat 自己的最短路径绘制**（`draw_shortest_path=False`），原因见 `config.py`：
  它画的是**直线穿墙**，且调色板索引 `MAP_SHORTEST_PATH_COLOR = 7` 落在默认填充色
  `[150,150,150]` 上、与可行走区域的灰完全同色，**画出来是隐形的**。改由本目录用
  `find_path` 画一条真正的测地路径（橙黄）。
